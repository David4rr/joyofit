# JoyoFit feature candidates from Huawei Health 17.0.8.300

Status: **static analysis only, nothing here is captured from a watch.** APK `huawei-health.apk` (v17.0.8.300), decompiled with
jadx-headless-mcp 0.7.1; class names are the R8-obfuscated ones (`defpackage.xxx`) plus the log tags the code prints. Dumps are in
`/home/dzul/re/huawei-health/src/`. Compared against Gadgetbridge at `/tmp/gb` (`devices/huawei/packets`, `service/devices/huawei/{datasync,p2p}`)
and `watch-fit/protocol/README.md`.

Confidence: **H** = read in the decompiled code, **M** = code read but one hop (schema, gate, or watch behaviour) not seen, **L** = string-level only.
"GB has / GB lacks" means present or absent in the `/tmp/gb` checkout (grepped for the package names and ids).

## 0. Read this first: transports and prerequisites

Three transports carry everything below. JoyoFit state (README): it has DataSync `0x37/01` for find-device only, FileUpload `0x28` (watch faces),
FileDownload `0x2C/0x0A`, Weather, Notifications, Alarms, Workouts. It has **no** `0x37/02..05` builders, **no** receive path for watch-initiated
`0x37` messages, and **no** P2P (`0x34`) stack.

| Transport | Wire | Gate (GB `HuaweiState`) | What JoyoFit must add |
|---|---|---|---|
| **DataSync `0x37`** ("Sample" commands in Huawei Health, `defpackage.yoq` builder, `eeu` proxy) | `37/01` SampleConfig `{src pkg, wear pkg, 0x83{0x84{05 configId i32, 06 action 1B (1 set, 2 query), 07 data bytes, 08 modifyTime i64}}}`; `37/02` SampleEvent `{src, wear, 03 eventId i32, 04 level 1B, 05 data}`; `37/03` SamplePoint (dict point, see DIET_PROTOCOL.md); `37/04` DictionaryPointInfo; `37/05` CompactDataDictionary | ExpandCapability **83** config, **84** event, **85** point/data, **173** dict | `0x37/02..04` builders + an inbound dispatcher keyed by `(src pkg, wear pkg)` (GB `HuaweiDataSyncManager.registerCallback(pkg, …)`). Both directions use the same frames; "src" is the side that sends. |
| **P2P `0x34/01`** (HiWear "WearEngine", `com.huawei.unitedevice.manager.EngineLogicBaseManager`) | TLV `01 cmd (1 ping, 2 send, 3 reply)`, `02 seq i16`, `03 src pkg`, `04 dst pkg`, `05/06 fingerprints` (cmd 2 only), `07 payload`, `08 resp code` (GB `packets/P2P.java`). Phone-side package is always `"hw.unitedevice." + module` and local fingerprint `"UniteDeviceManagement"` (`EngineLogicBaseManager` constants `UNITE_DEVICE_PACKAGE`, `UNITE_DEVICE_FINGER_PRINT`). Files go through `0x28` FileUpload with src/dst package + fingerprint fields (GB `HuaweiP2PFitnessData.sendCurrentTrack`) | SupportedCommands `34/01` (**the Fit 4's SupportedServices in the README observation contains `34`**) | P2P stack (register module, ping, send, receive, file send). One-time cost; unlocks rows 5, 9, 11, 19-25 |
| **Classic services** | their own service ids (`0x32` Menstrual, `0x25` Music, `0x09` OTA, `0x0F` Weather, …) | SupportedCommands per command | per feature |

**Caveat that applies to every DataSync row.** The README's 2026-10-14 SupportedServices list for the Fit 4 is `01 02 04 07 08 09 0a 0b 0c 0f 14 16 17 18 19 1a 1b 20 25 27 2a 2b 2e 30 32 34 35`;
it does not contain `37` (nor `28`/`2C`, which JoyoFit already uses), so DataSync availability is decided by ExpandCapability bits 83/84/85/173, not by that list. Read ExpandCapability on the Fit 4 Pro before building anything under `0x37`.
Whether the Fit 4 Pro supports each individual watch-side app (`hw.watch.*`) is **unknown** for every row; Huawei Health decides per product with `egs.e(deviceInfo, <bit>)` (bit numbers are quoted per row).

Encoding facts used throughout (read in `defpackage.ego`): event/config/point payloads are plain bytes; JSON payloads are sent as UTF-8 bytes
(`ego.a(ego.c(json))` = hex-of-UTF-8 → bytes), integers are big-endian (`ego.i(int)` = 4 bytes BE). Nested TLVs use `cqe`/`egq` with container tags `0x81…0x84`.

## 2. Detail for the rows that matter most

### 2.1 DST / time-zone (row 4), the cheapest win
`ndg.d()` builds `{"dst_in": nextTransition.toEpochSecond(), "time_offset": offsetAfter.totalSeconds}` (both `0` when the zone has no upcoming transition), wraps it in a SampleEvent
(`src hw.unitedevice.dstsync`, `wear hw.watch.dst.sync`, `eventId 800100020`, `level 0`) and sends it with `yoq.c(egd)`. The trigger is a watch event with the same id and `level == 0`
(`onDataReceived`). It is gated on ExpandCapability 84. Wire (reusing JoyoFit's frame layer; tag numbers for SampleEvent from the yoq decode in DIET_PROTOCOL.md: tag 3 eventId int32, tag 4 level 1 byte, tag 5 data bytes):
`37 02 | 01 <len> "hw.unitedevice.dstsync" | 02 <len> "hw.watch.dst.sync" | 03 04 2F B0 8E B4 (800100020) | 04 01 00 | 05 <len> <UTF-8 JSON>`.
Tag 1 = phone package, tag 2 = watch package, as in the diet card (DIET_PROTOCOL.md §3); not separately verified for this event.

### 2.2 Activity-ring goals (row 3)
Per-goal sends match GB's `HuaweiDataSyncGoals.sendCommonData`: SampleConfig action 1, one config per goal, data `01 <time i32 s> 02 <goal i32>`
(`SportGoalMgr` lines 279-298 build the same structure). The three-ring bundle `900200002` (steps, intensity minutes, stand hours) is `mdn.d(int[])`:
`01 time`, then `0x82{0x83{04 type 05 value} ×3}` with types `{1, 3, 4}`.
Calories goal in GB is sent as kcal×1000 (`sendCaloriesBurntGoal`); Huawei Health reads it back as `900200007`. The watch also writes its own goal back
(listener registered on `SyncStrategy.SRC_PKG_NAME` in `mdn.a()`), so JoyoFit needs the inbound callback to stay in sync.

### 2.3 SOS (row 7)
Two independent features, both read end to end:
- `mtt` registers a listener for `hw.unitedevice.sos`; watch → phone config carries `{"fallDetectionSwitch": 0|1, "timeStamp": ms}`; phone stores it (`ral.a("9005","900500038",…)`) and on connect answers a query by sending the stored value with action `1` (or action `2` with no data when nothing is stored): `mtt.e(boolean, deviceInfo, int, long)`.
- `nev` is an SMS relay: the watch sends event `800100040` from `hw.watch.safetyguard` with JSON containing `phoneNumber` and `content` (fields `getString("phoneNumber")`, `getString("content")`); `nev.c(...)` sends it with `SmsManager.divideMessage`, a `PendingIntent` result per part, and the phone replies with the same event id from `hw.unitedevice.safetyguard` adding `"status": "0"` on success / `"1"` on any failure (`nev.d(String,String)`). Failure reasons it reports: no `SEND_SMS` permission, empty number/content, SIM not ready (`SimState == 5`).

### 2.4 Menstrual (row 6)
Service `0x32` command map read in `neh` (`HwMenstrualManager`): `01` switches (tag `01`, value = Σ switch × `b(i)` weights, i.e. a bitfield: master, period-start remind, period-end remind, fertile-start remind, fertile-end remind, optional easy-pregnancy), `02` ModifyTime (tag `01` = 4-byte time, or `7F`=`150001` on error), `03` status data, `04` empty "update notice" (watch then asks), `05` capability (GB sends `01 = 02`), `06`, `07`, `08` (not read). Command `03` data: tag `01` = encoded cycle list (`nec.c`), container `0x82` with repeated `0x83{04,05,06,07 = four 4-byte values, 08 = 1-byte type, 12 = optional flag}`, tag `09` = modifyTime, tags `0a`/`0b` = one byte each (meaning not decoded, written only when the caller passes two flags). The phone also answers the watch's dictionary query for `400018` (`neb.onDataReceived`: filter `commandId == 4`, src `hw.watch.health.physiological`, wear `hw.unitedevice.physiological`; reads `getMenstrualFlow(start, end, modifyTime)`, sorted by start, at most 10 rows, each `ega(start, end, modified)` + `ege(type, 4-byte BE int)`). Watch → phone flow edits arrive in the same dict.
The inner meaning of the `nej` fields (the four 4-byte values at `04..07`) is **not** decoded here.

### 2.5 Training plans and courses (row 9), what one push looks like
`iiz.e(FitWorkout, …)`: file name `<messageId>courseInfo.bin`; content = `dft` header (36 bytes little-endian, fields in order `businessType (3 for a custom course)`, `version`, `totalLength`, `businessHeadLength`, `messageId`) + `CourseDataForDevice.CourseStorageInfo` protobuf; sent as a P2P file with `yod.d.e(File)`, the receiver is `in.huawei.fitness`. Handshake (`d(Plan,…)`) is a byte message (no file) with the same header, business type `1` and `PlanShakeHandsInfo`. After each file the phone waits for a watch ack through `dfs` (`SportBaseEngineManager.sendCommandToDevice`, result 207 = success). The watch pulls the weekly plan only after the DataSync trigger `800200002` on devices with ExpandCapability 295; older products use `PlanSendService`'s handshake+push directly.

### 2.6 Health Glance (row 8), what the JSON looks like
`ird` (Gson `@SerializedName`): `height` (int cm), `weight` (float kg) + `weightTimestamp`, `bodyMassIndex` (float, computed in `irw.i`), `fatPercentage` + `fatPercentageTimestamp`, `systolicPressure`, `diastolicPressure`, `bloodPressureGrade`, `bloodPressureSource` (0 = manual), `bloodPressureTimestamp`, `fattyLiverRisk`, `fattyLiverGrade`, `fattyLiverTimestamp`, `sleepApneaGrade` + `sleepApneaTimestamp` (only sent when `Utils.n()` = overseas build). Weights read from HiHealth type `2004` over the last 30 days.
